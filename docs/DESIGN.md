# 拖拽导入 · 插件功能设计

> 插件建议标识：`siyuan-drag-import` ｜ 显示名「拖拽导入」
> 目标平台：Windows 桌面版思源（Store 版 / 安装版）；移动端不做
> 文档版本：v0.1 草案 —— 结构已定型，标 ⚠ 的条目需要在真机上验证后再冻结

---

## 0. 一句话定位

把「导入 Markdown」从 **5 次点击 + 逐层选路径的弹窗**，压成 **一次拖拽**：
从资源管理器把 `.md` / 文件夹 / `.zip` 拖到左侧文档树，松手即入库，层级和文件名照原样还原。

---

## 1. 目标与非目标

| | 内容 |
|---|---|
| 目标 1 | 单文件、文件夹、压缩包三类来源，拖到文档树即导入 |
| 目标 2 | 文件夹 / 压缩包的**目录层级原样还原**成思源文档树 |
| 目标 3 | 全程可见：投放高亮 → 逐篇进度 → 成功/失败清单 |
| 目标 4 | 出问题能自救：不中断、不丢流程、有日志可查 |
| 非目标 | 不做 docx / pdf / html 转 md（交给官方导入与 pandoc） |
| 非目标 | 不做 `.sy.zip` 完整包还原（v1 只提示走官方导入，见 §4.3） |
| 非目标 | 不做网络位置 / 网盘映射盘的批量导入（可跑，但慢，见 §9） |
| 非目标 | 不替代官方「导入」弹窗，两者并存 |

设计原则：**导入是「可回滚的批量建文档」，不是「文件搬运」**。任何一步失败都不能让已成功的部分变得不可解释。

---

## 2. 交互总览

```
① 拖入          ② 悬停高亮        ③ 释放           ④ 扫描        ⑤ 导入        ⑥ 结果
资源管理器 ──▶  文档树描边+      ──▶ 立即收起高亮 ──▶ 解析来源    ──▶ 逐篇建文档 ──▶ 卡片汇总
                目标行标注          弹出进度卡片      （异步）        （可取消）      （可撤销）
```

关键取舍：**释放后立刻收起高亮、立刻出卡片**。哪怕扫描 200 个文件要 1 秒，也必须先给「我收到了」的反馈——这是拖拽体验里最容易崩的一环。

## 3. 拖拽监听与投放区域

### 3.1 监听范围

| 项 | 决策 | 原因 |
|---|---|---|
| 监听层级 | `document` 上 **捕获阶段** 监听 `dragenter / dragover / dragleave / drop` | 思源内部可能 `stopPropagation`，冒泡阶段会漏 |
| 生效条件 | 指针落在文档树面板内（`closest(".sy__file")`）且 `dataTransfer.types` 含 `Files` | 只接管「从系统拖文件」，不干扰思源自己的文档拖动 |
| 编辑器区域 | **不接管**，保持原生行为（拖图进正文仍是插图） | 避免破坏既有习惯 |
| 兜底 | 文档树之外的文件 drop 一律 `preventDefault()` | 防止 Electron 把窗口导航到 `file://`，把整个界面刷掉 |

**✅ M0 已验证（SiYuan 3.8.8）**

- 选择器：面板 `.sy__file`，条目容器 `.file-tree__items`，行 `[data-node-id]`（源码里 `closest(".sy__file").querySelector(".file-tree__items")`）。仍集中放在 `selectors.ts`。
- 全量扫描 5 个前端 chunk：**没有任何常驻的 document / window 捕获拖拽监听**，文件树自身的 drop 在冒泡阶段且只认内部 MIME 类型，外部 `Files` 被直接忽略 → 捕获阶段一定抢得到。
- **capture `dragover` 必须自己 `preventDefault()`**：思源对外部文件的 dragover 不 preventDefault，不改这一行，光标是"禁止"态，`drop` 根本不触发。
- 文件树的 `drop` 是无条件 `preventDefault + stopPropagation` 的，所以「拖文件把窗口导航走」在树上今天不会发生；但我们接管后应 `stopPropagation()`，避免触发它后面的空移动逻辑（`drop([])`）。树以外的区域没有这层保护，全局兜底仍是必要项。

### 3.2 事件状态机

```
idle ──dragenter(文件)──▶ hovering ──dragover──▶ hovering（维持）
                            │  ▲
                    dragleave│  │dragenter(子元素)
                            ▼  │
                       leavePending ──(60ms 内无 dragenter)──▶ idle
                            │
                          drop ──▶ importing ──▶ done / cancelled
```

- 用 **深度计数 + 60ms 延迟** 消除 `dragleave` 在子元素间穿梭导致的闪烁（经典坑，必须做）。
- `drop` 时同步 `preventDefault()` 并取 `dataTransfer`，**先把 File 对象全部抓取到数组里**，再异步处理——事件对象在异步回调里可能已失效。

### 3.3 三层视觉反馈

| 层 | 表现 | 说明 |
|---|---|---|
| 面板层 | 文档树整体加 2px 主色内描边 + 4% 主色底 + `cursor: copy` | 一眼看到「可以放这儿」 |
| 目标行层 | 鼠标下方命中的节点（笔记本 / 文档）加主色描边；笔记本行额外显示底部插入线 | 明确「落到哪一层」 |
| 跟随提示 | 面板顶部出现一条窄横幅：`释放以导入到「知识库」/ 根目录`；右侧显示识别到的类型（`文件夹` / `压缩包` / `1 个 Markdown`） | 不跟随鼠标（跟随会让长文件名遮挡内容） |

> 悬停阶段**不显示文件数量**。数文件必须遍历目录，dragover 每秒触发几十次，做异步计数只会抖。数量在释放后的「扫描」阶段一次给出。

### 3.4 与原生行为的共存约定

- 内部拖动（拖动已有文档、拖动块）没有 `Files`，直接放行。
- 从浏览器拖图片/文字到文档树：没有 `Files`，放行（不处理）。
- 拖动中按 `Esc`：立刻回到 `idle`，不发请求。

## 4. 三类来源识别与处理

### 4.1 判定顺序

```
for each DataTransferItem:
  entry = item.webkitGetAsEntry()
  if entry.isDirectory        → ① 文件夹
  else if 扩展名 ∈ 压缩包白名单 → ② 压缩包
  else if 扩展名 ∈ md 白名单    → ③ 单文件
  else                        → 忽略（记入「已跳过」）
混合拖入：三类同时存在时全部接受，按「先解包、再目录、最后散文件」顺序排队，
        合并成一次任务、一个进度卡片、一份汇总。
```

### 4.2 取到真实路径的两条路（M0 已定：主备对调）

| 路线 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| **A（主）** | `require("electron").webUtils.getPathForFile(file)` → Node `fs.readdir({withFileTypes:true})` 递归 | 快；保留 mtime；能识别空目录；**与思源官方处理拖拽的方式完全一致** | 依赖 `nodeIntegration`（桌面端为 `true`，已验证）；浏览器/移动端不可用（本插件不做这两端） |
| **B（兜底）** | `webkitGetAsEntry()` 递归 `createReader().readEntries()` | 纯浏览器 API，无 Node 依赖 | 大目录慢；空目录拿不到；`readEntries` 每次最多 100 条，必须循环读到空数组 |

依据：SiYuan 3.8.8 主进程 `webPreferences` 为 `nodeIntegration: true, contextIsolation: false`；官方前端在外部文件拖拽处用 `webUtils.getPathForFile`（3 处），`webkitGetAsEntry` 出现 **0 次**。

两条路产出一致的 `SourceNode` 中间结构，后续逻辑完全共用。启动时探测 `webUtils.getPathForFile` 是否可用决定走哪条，并写进日志。

### 4.3 压缩包处理

| 格式 | v1 | 说明 |
|---|---|---|
| `.zip` | ✅ 支持 | 主力格式（Windows 右键「压缩为 ZIP」） |
| `.tar.gz` / `.tgz` | ⚠ 可选 | `fflate` 可直接解开，成本低，建议一并支持 |
| `.rar` / `.7z` | ❌ | 纯 JS 无成熟解压；提示「请先转成 zip」 |
| `.sy.zip` | ❌ 转交 | 识别后提示「这是思源导出包，请用 设置 → 导入」 |

解压实现要点：

1. **纯内存为主**：`fflate.unzipSync(Uint8Array)`。单包 ≤ 200 MB 直接内存解；超过则改用 `unzip` 的流式回调，边解边判上限，超限即中止。
2. **文件名编码**（中文用户必踩）：ZIP 条目的通用标志位 bit 11 表示 UTF-8。未置位时按 **GBK/CP936** 解码（`new TextDecoder("gbk")`，Chromium 原生支持）。不处理这一步，用 Windows 自带压缩打的包会全是 `鏂囨。` 乱码。
3. **安全闸门**（必须在解压前做，不能事后补救）：
   - 条目路径含 `..` 或绝对路径 → 直接判为非法包，整包拒收；
   - 条目数 > 5000、解压后总量 > 500 MB → 判为可疑包，提示后拒收；
   - 加密条目（bit 0 置位）→ 「加密压缩包暂不支持」，整包拒收。
4. **包内结构还原**：
   - 包内只有一个顶层目录 → 以该目录为导入根（不套「压缩包同名」这一层，避免 7-zip 常见的双层套娃）；
   - 包内多个顶层条目 → 建一个名为「压缩包文件名（去扩展名）」的父文档，各条目挂在下面。
5. **过滤**：`__MACOSX/`、`.DS_Store`、`Thumbs.db`、`desktop.ini`、`._*` 直接丢弃，不计数、不报告。
6. **失败即回滚**：解压失败 / 校验失败 → 一篇都不建。不做「能解多少算多少」，那会让用户面对半棵树无从判断。

## 5. 存放位置与层级结构

### 5.1 目标笔记本判定（优先级从高到低）

1. 松手位置命中的**文档节点** → 目标 = 该文档的所属笔记本，父层级 = 该文档；
2. 松手位置命中的**笔记本行** → 目标 = 该笔记本，父层级 = 根；
3. 当前文档树正在展示的笔记本 → 根；
4. 都没有 → 弹出笔记本选择（单选），不猜。

> 已关闭的笔记本不可作为目标：命中的是关闭状态时，提示「该笔记本已关闭，请先打开」，不自动打开（打开笔记本是有副作用的操作，交给用户）。

### 5.2 来源结构 → 文档树结构

思源没有真正的「文件夹」实体，**有子文档的文档就是文件夹**。所以层级映射就是把目录变成「父文档 + 子文档」。

| 拖入 | 结果 |
|---|---|
| `笔记.md` | `根/笔记` |
| `项目A/`（含 `a.md`、`b.md`、`spec/c.md`） | `根/项目A`（父文档）→ `a`、`b`、`项目A/spec`（子父文档）→ `c` |
| `项目A/` 只有 `a.md` | 同上，`项目A` 仍作为父文档保留（**不为省一层而拍平**，否则重名必冲突） |
| `pack.zip`（内含 `项目A/`） | 同「拖入 项目A/」 |
| `pack.zip`（内含 `a.md`、`img/`） | `根/pack` → `a`；`img/` 若不是资产目录则建 `pack/img` |
| 混合拖入 | 各自按上表落到同一父层级下，互不嵌套 |

**父文档命名 = 原目录名**；若父文档已存在，按 §7 冲突策略处理，并且**子文档继续往已存在的父文档里放**（这是用户最自然的预期：再拖一次只是补文件）。

### 5.3 文档命名规则

按顺序处理，每步都可能改变名字，处理完再判重：

1. 去扩展名（`a.md` → `a`）
2. Unicode **NFC** 归一化（macOS 传来的文件名是 NFD，不归一化会导致「看起来一样的两个名字」）
3. 剔除 `.` 与 `..` 段落（**必须做**：实测 `/边界/../逃逸` 会被内核当作路径上跳，直接把文档建到根层，破坏层级还原）
4. 清除思源/Windows 非法字符 `<>:"/\|?*`、控制字符 → 替换为 `_`
5. 去掉首尾空白与结尾的 `.`；`CON/PRN/AUX/NUL/COM1…` 等保留名加前缀 `_`
6. 长度 > 120 字符 → 截断到 120 + `…`（**内核不截断**：实测 300 字标题原样保留，会把树撑坏）
7. 空名 → `未命名`（内核会把纯空白变成「未命名文档」，多个空名会撞在一起，必须我们自己起名）
8. 最后做冲突判定（§7）

> M0 实测：内核只做「trim」和「纯空白 → 未命名文档」两件事，其余（长度、`.`/`..`、纯空白）一律不管；`<` `"` 会在存储时转义成 `&lt;` `&quot;`，但 API 的 hpath 收**原文**——所以我们不要自己 HTML 转义，否则会双重转义查不到。

### 5.4 建文档顺序（M0 已验证，可大幅简化）

**结论：`createDocWithMd` 传完整 hpath 会自动补建父文档，且已存在的父级会被复用、不报错。**

实测 `/L1/L2/L3` 后磁盘上出现 3 个 `.sy`、三层嵌套；再往 `/项目A/子目录` 下追加文档同样成功，父级复用。

所以：

```
逐篇直接 createDocWithMd(notebook, "/根/子/孙/文档名", markdown)
父级由内核补建 / 复用，插件不再逐层「先查后建」
唯一例外：空壳目录（空文件夹、或只含图片的目录）需显式建一个父文档，
         因为没有 md 文件能把这条路径「带出来」
任一文档创建失败 → 该篇计入失败，后续继续（不做整体回滚）
```

省掉每篇一次「查父文档」的往返：500 篇规模下约省 500 次请求（M0 实测单篇 32.6ms）。

**硬约束（实测）**：`path` 为空字符串会建出一个标题为 `.` 的文档；`path: "/"` 也会建出异常命名的文档。planner 必须保证 path 至少有一段，否则拒绝发送。

## 6. md 文件范围与格式转换

### 6.1 扩展名白名单

`.md` 必收；`.markdown` / `.mdown` / `.mkd` 默认收；`.txt` **默认不收**（可选开启，开启后按纯文本导入，仅做最基础的换行/标题识别）。其余一律进「已跳过」清单，附带原因。

### 6.2 编码（中文场景的高频崩点）

```
读 ArrayBuffer
 → UTF-8 BOM？ 去 BOM，按 UTF-8 解
 → 无 BOM：TextDecoder("utf-8", {fatal:true}) 试解
     成功 → UTF-8
     抛错 → TextDecoder("gbk") 兜底（覆盖 GB2312/GBK/GB18030）
 → 仍失败（含大量 \u0000）→ 判定为二进制，跳过并报告
```

绝不使用 `File.text()` 直接读——它假设 UTF-8，GBK 文件会静默变成乱码入库，比报错更糟。

### 6.3 Frontmatter

默认：**剥离 YAML frontmatter**，写入文档属性（`title` → 文档名候选；其余 → 自定义属性 `custom-<key>`），原始内容存入文档自定义属性 `custom-source-frontmatter` 备查。
可选设置：保留为正文开头的代码块（给需要原样搬运的场景）。
理由：思源不解析 frontmatter，原样保留会在正文顶部挂一大坨 YAML；剥离后再落到属性里，信息不丢且不碍眼。

### 6.4 标题与首行 H1

思源文档名 = 树上的名字，正文不需要再重复一遍标题。
规则：若正文第一段是**唯一且以 `# ` 开头的一级标题**，且其文本与文件名相似（去空白/标点后相等或互为前缀）→ 移除该行。否则保留。默认开启，可关。

### 6.5 图片与附件（决定「导入完还能不能看」）

| md 中的写法 | 处理 |
|---|---|
| `![](./img/a.png)`、`![](attachments/a.png)` | 本地存在 → `/api/asset/upload` 上传 → 重写为 `assets/a-20261024153012-x7f2.png` |
| `![](https://…)` | 原样保留；可选「下载外链图片」（v2） |
| `![](data:image/png;base64,…)` | 解码 → 上传 → 重写（可选，默认开） |
| `![[a.png]]`（Obsidian 嵌入） | 转成标准 `![](…)` 后再走上传 |
| 目标文件不存在 | 保留原路径 + 在结果里列为「1 张图片缺失」，不阻断导入 |

同名资源自动重命名交由 `/api/asset/upload` 的 `assetsDirPath` 机制处理，避免不同目录下的 `image.png` 互相覆盖。

### 6.6 其他语法转换矩阵

| 语法 | v1 处理 |
|---|---|
| 标准 Markdown / GFM 表格 / 任务列表 | 思源原生支持，直接落库 |
| `$...$` / `$$...$$` 公式 | **内核不转换**（实测原样落成普通文本），需插件转成思源公式 `\(...\)` / `\[...\]` |
| YAML frontmatter | **内核不识别**（实测渲染成两条分隔线 + 一段文本），按 §6.3 自行剥离 |
| `> [!note]` 等 Obsidian callout | 转为引用块 + 首行加粗（`> **Note**`） |
| `#tag` | 保留文本；可选转思源标签（设置项，默认关，避免误伤 `#include`） |
| `[[双链]]` | v1 原样保留为文本；v2 若目标文档在同批次内，转 `siyuan://blocks/<id>` |
| `[文字](other.md)` | v1 保留；同批次内命中则改写为 `siyuan://blocks/<id>`（v2） |
| 内联 HTML | 交给思源渲染（思源本身支持 HTML 块） |
| 脚注 `[^1]` | 保留原文（思源无脚注，渲染为文本+链接） |

### 6.7 明确不做的转换

md → 思源块引用的「智能拆分」（把 `## 标题` 拆成独立文档）、多文件合并、目录页生成。这些属于「重组」而非「导入」，交用户手动处理。

## 7. 重名与同名冲突

### 7.1 判定口径（M0 实测后改写）

冲突 = **同一父层级下，规范化后的文档名相同**。
规范化 = NFC + 去首尾空白 + 英文小写化（Windows 文件系统大小写不敏感，`Readme` 和 `readme` 在资源管理器里就是同一个，必须按同一口径判）。

**内核不做任何去重、也不做归一化**：实测同一 hpath 连建两次都成功，得到两个 id；`getIDsByHPath` 是精确匹配——`/口径/readme`、`/口径/ Readme ` 都查不到已存在的 `/口径/Readme`。

所以判定必须由插件完成，分两层：

1. **同级名字集合**（主判据）：进入某个父层级时取一次该层的子文档名单，转成 `小写化 + NFC + trim` 的 Set 缓存，逐篇在 Set 里判重；本批次新建的名字同时写回 Set（批次内重名也靠它）。
2. **精确复核**（兜底）：真正建文档前用 `getIDsByHPath(原始大小写)` 再确认一次（1.5–2.3ms），防止「缓存拿到的名单已经过期」。

**不要用 SQL 预查**：实测索引比写入滞后 0.3–1 秒，500 篇建完立刻 `count(*)` 只有 468 条。用 SQL 做同批次重名判定必然漏判。

**取同级名单的可行方式**：`listDocsByPath`（注意它的 `path` 参数是**存储路径** `/2026xxx-id.sy`，不是 hpath，传 hpath 会静默返回空数组）；或对目标父路径逐个 `getIDsByHPath`。

### 7.2 四种策略

| 策略 | 行为 | 适用 |
|---|---|---|
| **自动改名**（默认） | `笔记` → `笔记 (2)` → `笔记 (3)`…；内部计数，不重复查询 | 绝大多数场景：备份/多来源合并 |
| **跳过** | 保留原文档，本文件不导入，计入「已跳过」 | 增量补库，怕污染已有内容 |
| **追加** | 内容追加到已有文档末尾，插入分隔：`\n\n---\n\n> 以下内容来自 xxx.md（2026-10-24 15:30 导入）\n\n` + 正文 | 同一篇笔记的多版本合并 |
| **覆盖** | 清空原文档正文后写入 | 高风险，默认隐藏；选中时二次确认「不可撤销」 |

交互：只有真正发生冲突才弹一次「冲突处理」小卡片，列出冲突项（最多 5 条 + 「等 N 项」），单个选择 or 「全部应用」。**无冲突时完全不打扰**。

### 7.3 批次内部重名

`a/笔记.md` 和 `b/笔记.md` 都被导入到同一父层级时同样会撞名——判定要把「本批次已占用的名字」计入集合，不能只查数据库。

### 7.4 父文档重名

父文档已存在 → 不新建，把子文档挂进去（视为「合并文件夹」）。这条要写死在逻辑里：它是用户重复拖同一个文件夹时唯一合理的预期。

## 8. 进度反馈与结果提示

### 8.1 阶段机

| 阶段 | 显示 | 可取消 |
|---|---|---|
| 扫描 | `正在读取 项目A…`（不定长滚动条） | ✅ |
| 决策 | 冲突卡片（如有） | — |
| 导入 | `正在导入 12/48 · 03-设计稿.md`，确定性进度条 | ✅ |
| 收尾 | `正在整理结果…`（<200ms） | ❌ |
| 完成 | 结果卡片 | — |

进度分母 = **文件数**（不是字节数）。图片上传算作所属文件的子步骤，不单独占进度，避免进度条来回抽搐。

### 8.2 组件规格

- 位置：右下角浮动卡片，宽 360，圆角 8，轻阴影；**不遮挡文档树与编辑器主体**。
- 卡片头：`正在导入 48 篇` + 折叠箭头 + 关闭（关闭 = 后台继续，不是取消）。
- 主体：当前文件名（单行省略，中间截断保留扩展名）+ 进度条 + `12 / 48`。
- 底部：`取消`（文本按钮，弱化）。
- 单篇耗时 > 800ms 才显示文件名细进度，短任务不闪。
- 卡片可拖动？不做。可折叠到左下角小圆点？做，长任务时避免挡视线。

### 8.3 结果汇总

```
✅ 导入完成        成功 45 · 跳过 2 · 失败 1
────────────────────────────────────
失败 1
  项目A/spec.md      文档名过长，已跳过
跳过 2
  img/cover.png      非 Markdown
  __MACOSX/…         系统文件
────────────────────────────────────
[打开第一篇]  [撤销本次导入]  [查看日志]
```

- 「打开第一篇」：`openTab` 打开本次第一个成功创建的文档，给一个明确的「去哪儿找」。
- 「撤销本次导入」：**保留 5 分钟**，期间可一键删除本次创建的所有文档。5 分钟后按钮置灰，提示「已过期，请到文档树手动删除」。
  **M0 实测：删除一个文档会连带删除它的所有子文档。** 因此撤销必须维护两个集合：
  - `createdIds`：本次新建的文档 → 可以删；
  - `reusedParentIds`：本次**复用**的已存在父文档 → **绝对不删**（删了就是删用户原有内容）。

  安全做法：只删 `createdIds` 中「父级不是 reused」的最顶层那批（删父即连带删掉本批次建在其下的子文档），再清点剩余。
- 「查看日志」：内置弹窗展示本批次 JSONL 日志，可复制。

### 8.4 日志（Store 版没有 F12，落盘是唯一可靠通道）

- 路径：`data/storage/petal/siyuan-drag-import/logs/import-<yyyyMMdd-HHmmss>.jsonl`
- 每行一个事件：`{ts, phase, file, action, result, ms, err?}`
- 只保留最近 20 个批次，自动清理；不记录正文内容（隐私）。

## 9. 异常处理矩阵

| 情况 | 检测点 | 用户可见行为 | 是否中断 |
|---|---|---|---|
| 拖入非 md 文件 | 扩展名判定 | 计入「已跳过 · 非 Markdown」 | 否 |
| 文件夹里夹着图片/附件 | 扩展名 + 资产目录名（`assets/` `attachments/` `img/` `images/` `static/`） | 不建文档；被 md 引用时上传为资源 | 否 |
| 压缩包损坏 | `fflate` 抛错 / CRC 校验失败 | 卡片：「压缩包已损坏，未导入任何内容」 | 整包回滚 |
| 加密压缩包 | 条目 bit 0 | 「加密压缩包暂不支持，请先解压」 | 整包拒收 |
| 压缩包路径穿越 | 条目名含 `..` / 绝对路径 | 「压缩包结构异常，已拒绝」 | 整包拒收 |
| 压缩包炸弹 | 条目数 / 解压体积超阈值 | 「压缩包过大（>500MB 或 >5000 项）」 | 整包拒收 |
| 非 zip 压缩格式 | 扩展名 + magic number | 「暂不支持 .rar/.7z，请转成 zip」 | 该来源跳过 |
| 无读取权限（EACCES/EPERM） | Node `fs` 错误码 | 逐条累计：「3 个文件无读取权限（可能被其他程序占用）」 | 否 |
| 文件被占用（EBUSY/EPERM） | 同上 | 同上，附文件名 | 否 |
| 文件过大（>20MB 单篇） | size 检查 | 默认跳过并提示，可在设置放开（超过后建文档会明显卡） | 否 |
| 网络盘 / 映射盘超时 | 单文件 10s 超时 | 跳过并标注「读取超时」 | 否 |
| 路径超长（>260 字符） | 遍历时 | 跳过并提示「路径过长」，建议缩短后重试 | 否 |
| 空文件夹 | 目录遍历 | 不建文档，计入「已跳过 · 空文件夹」 | 否 |
| 清洗后名字为空 / path 为空 | planner 校验 | 名字兜底「未命名 N」；path 为空直接拒发（实测会建出标题为 `.` 的垃圾文档） | 否 |
| 目标笔记本已关闭 | 笔记本状态检查 | 「请先打开该笔记本」，本次不执行 | 整个任务 |
| 内核报错 / 版本不匹配 | HTTP 非 0 code | 该篇计入失败；连续 3 次失败则中止 | 连续失败时中止 |
| 磁盘写入失败（ENOSPC） | 内核返回 | 「磁盘空间不足，已中止」，保留已建文档 + 提供撤销 | 整个任务 |
| 误拖到编辑器外空白区 | 全局兜底 | 静默忽略（仅 `preventDefault`），不弹提示 | — |

设计约定：**能局部失败就不整体失败**，但「来源不可信」（损坏包、路径穿越、加密包）必须整包回滚——半截数据比没有数据更难收拾。

## 11. 技术架构与接口对照

```
index.ts            插件入口、注册设置、注册 DOM 监听
drop/
  controller.ts     事件状态机、命中判定、拖拽视觉
  selectors.ts      文档树 DOM 选择器（集中管理，便于修）
source/
  analyze.ts        DataTransfer → SourceNode[]（三类来源归一）
  fsWalk.ts         路线 B：Node fs 遍历（能力探测）
  entryWalk.ts      路线 A：webkitGetAsEntry 遍历
  archive.ts        zip 解包、编码修正、安全闸门
import/
  planner.ts        生成「建文档计划」：层级、命名、冲突决策
  executor.ts       逐条执行、进度回调、取消、失败累积
  markdown/
    encoding.ts     BOM/UTF-8/GBK 判定
    transform.ts    frontmatter、H1、callout、图片链接重写
  api.ts            对内核 API 的薄封装（超时、重试、错误归一）
ui/
  overlay.ts        三层拖拽视觉
  progress.ts       进度卡片（含折叠、取消）
  summary.ts        结果卡片（含撤销倒计时）
  conflict.ts       冲突选择卡片
logger.ts           JSONL 落盘 + 清理
```

| 用途 | 接口 |
|---|---|
| 列笔记本 | `POST /api/notebook/lsNotebooks` |
| 建文档 | `POST /api/filetree/createDocWithMd`（`notebook` + `path`(hpath) + `markdown`） |
| 查重名 | `POST /api/filetree/getIDsByHPath`（精确、区分大小写、不去空格、1.5–2.3ms）为主；同级名单用 `POST /api/filetree/listDocsByPath`（`path` 必须是存储路径） |
| 取正文（追加策略） | `POST /api/filetree/getDoc` 或 SQL 取块 → `getBlockKramdown` |
| 上传资源 | `POST /api/asset/upload`（multipart，`assetsDirPath` + `file[]`），**只信返回的 `succMap`** |
| 撤销 | `POST /api/filetree/removeDocByID`（`{id}`）。注意 `removeDoc` 需要 `notebook` + `path`，用 id 调会报 `block not found`；且删除会**连带删除子文档** |
| 打开文档 | 前端 `openTab({app, doc: {id}})` |
| 轻提示 | 前端 `showMessage`（仅用于「已跳过」这类低价值信息，主力是卡片） |

> ⚠ 落地前用 `/api/system/version` 对应的 `api.md` 核一遍接口名与参数：`removeDoc` / `getDoc` 在不同版本命名略有出入。

## 14. 验收用例

1. 单个 `笔记.md`（UTF-8）拖到文档树空白处 → 根级出现 `笔记`，正文正确。
2. 单个 `笔记.md` 拖到某个文档上 → 成为该文档的子文档。
3. GBK 编码的 `老笔记.md` → 中文不乱码。
4. 带 frontmatter 的 md → 文档属性里有 `custom-*`，正文无 YAML。
5. 首行 `# 笔记` 且与文件名相同 → 正文不重复标题。
6. `![](img/a.png)` → 图片入库、链接指向 `assets/`，图片能显示。
7. 文件夹 `项目A`（3 层、8 个 md、2 张图、1 个 pdf）→ 层级一致，pdf 计入跳过，图片按引用上传。
8. 空文件夹 → 跳过并说明，不建空文档。
9. 再次拖入同一文件夹（已导入过）→ 父文档复用，文件名走 `(2)`，文档数翻倍但不产生冲突弹窗外的意外。
10. `pack.zip` 内含单个顶层目录 → 不出现双层套娃。
11. Windows 自带压缩的中文文件名 zip → 文件名不乱码。
12. 人为损坏的 zip → 「压缩包已损坏」且文档树零新增。
13. 加密 zip → 提示不支持，零新增。
14. 拖入 `.png` / `.pdf` / `.docx` → 全部进跳过清单，零新增。
15. 只读目录里的 md → 提示无权限，其余文件继续导入。
16. 导入第 10 篇时点取消 → 停止；已建 9 篇保留；结果卡片说明「已取消，已导入 9 篇」。
17. 导入完成后点撤销 → 本次创建的文档全部消失，之前已存在的同名文档不受影响。
18. 拖到编辑器正文 → 仍是原生插图行为，未被接管。
